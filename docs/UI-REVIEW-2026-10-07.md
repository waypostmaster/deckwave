# UI review, 2026-10-07: "far too many buttons, and it is not intuitive"

Read-only review of the main deck page (`index.html` + `assets/*.js`; RECON and citywalk out of scope), run as a 93-agent workflow on the keeper's request. **Nothing in the product was changed.** This file is the record; BUILD-LOG ledger 147 points here.

## Method and what it can and cannot claim

- **Map:** five code readers inventoried 184 controls with file:line; one agent inspected the live page on 127.0.0.1:8777 in Chrome (counts with `elementFromPoint` hit-tests, desktop and a 400 px iframe). The live page carried the keeper's saved state (`dw-cfg-open=1`), stated beside the counts.
- **Review:** six lens reviewers (first run, the keeper's routine, redundancy, labels/state, information architecture, accessibility/mobile) plus a **blind Codex CLI review** (codex-cli 0.160, `exec -s read-only`), which never saw the other findings.
- **Verify:** 92 raw findings merged to 38; each checked by two skeptics, one on the facts against the code, one on whether the proposal breaks something load-bearing. **0 refuted on the facts; 13 rated "partly" and corrected.**
- **Propose:** a synthesised redesign (Part 2), then a **Codex red-team** of that proposal (Part 3) and a completeness critic (Part 4). **Where Parts 3 and 4 contradict Part 2, they win** — Codex judged the proposal *not implementation-ready* and gave code-backed reasons.
- Not established: anything about how the redesign *feels* (no user has seen it), real phone behaviour (the 400 px pass was a desktop iframe — no coarse pointer, no phone UA), and the browser counts were taken on one saved state.

## Headline numbers (live page, measured)

- Desktop, settings drawer open (the keeper's saved state): **44 reachable controls** in the bar; about **63** counting glossary labels and the now-playing ✕. Drawer closed (a newcomer): **28**. 11 selects holding **84 options**.
- ~8–10 controls carry the orange accent, because `hot` means both "do this next" and "this toggle is on". **▶ demo — the only zero-setup way to hear anything — is not one of them.**
- 400 px with the drawer open: the first screen is 100% buttons and the panel area is **0 px tall** (`#tri` clientHeight 0).

Also, 'settle' (1624) is OFF by design (ROADMAP D8). Making it look more like a checkbox must not make switching it on look like a recommended step.

## 1. Diagnosis in five sentences

1. Every control is built by the same `btn()`/`select()` helper into one wrapping flexbox (`#tp`, 1303-1333). The groups are only a `data-grp` tag, so files, building, transport, backups, capture and diagnostics all carry the same weight. Counted from source, about 24 controls are visible on desktop with ⚙ closed. A live count gave 28 with the drawer closed and 44 open, roughly 63 if hover targets are included.
2. The one visual cue, the `hot` accent (152), means two things: "do this next" for scan, build, ▶ and save set, and "this toggle is on" for nine others, including the default-on call-pause toggle. About 8-10 things look primary. The zero-setup `▶ demo` (1402) is not one of them.
3. The real workflow (bring music → build → play) is never shown. Build only *prepares*, into a side card, and says "Playback unchanged." Three build buttons hide one command whose modes are explained only in a code comment (1445-1452). Controls stay enabled and refuse afterwards through a 9px, ellipsised log line (181-182). Those refusals mostly point back at the folder picker.
4. Mix-changing and device settings (tune, settle, keep duplicates, output, phone, call pauses) sit in a drawer named "⚙ display", next to theme and sprite. Some of them reset silently on reload. Toggles are worded as status sentences, and selects hide their names inside truncated option text.
5. Explanations are reachable only by mouse hover (bind() 2572-2577): the constructed-energy caveat, Essentia's confidence scale, and the reason a track plays straight. Panel controls are opacity:0 yet still tappable. The phone layout is the desktop bar folded, and a saved open drawer squashes the panels to 0px. So on touch and keyboard the screen is both crowded and unexplained.

## 5. State visibility fixes

1. **Two meanings, two treatments.** One filled "primary" (§2). For "on", use `aria-pressed` plus a dot or check. Live capture and render-in-progress use the **warn** colour, not a small dot. `aria-expanded`/`aria-controls` go on settings, now-playing and Set|Panels.
2. **Preconditions shown up front.** Use `aria-disabled` (still focusable, still clickable) plus a reason line. Never the real `disabled` attribute on ▶, which would lose the gesture-bound `armCalls`. ▶'s predicate is `!state.now && !dash.prepared && !dash.set.length`, using `state.now`, never `of`/`live`. One `refreshEnabled()` is called from every state change.
3. **One painter per visible state.** `syncPhl()`, plus compact, list select, now-playing, and the layout/density selects after `views.load`, are all painted from DOM state and called from the handler, `dash.prepare()` (1227-1232) and `onViewLoaded`. Un-compacting must also remove `mini-host` and hide `#nowline`.
4. **The ▶/❚❚ label follows state** on the existing 1 s tick. Paused (`suspended`) and stopped (`now === null`) are distinct: "▶ resume" vs "▶ play".
5. **Log line.** It wraps to two lines on desktop. `title` is updated in `step()` too, so a countdown never freezes. Scrollback holds only *resolved* countdown text. Non-countdown messages are mirrored to a polite region, with scan progress throttled.
6. **Build summary persists** in the Prepared header. It comes from `DW.inspect(candidate)`, is labelled "as built", and is cleared on Apply, Play and Discard. Showing it never prints a stretch figure against a straight track.
7. **Retargeting is explicit.** Set ▾ names its target ("prepared set · 31 tracks" / "current set"). The single target rule (`fileSet`) stays, because pinning to current would act on the older set after the most common flow.
8. **Committed route annotation** in the set list (destination, stones left, policy). It copies `panel-route.js:132-150` exactly: a scenic stone shows "full", a fast stone shows the engine-floor dwell, and the LIST ≠ DECK check comes first. It clears on completion or clearRoute and covers event-started routes.
9. **Selects that act.** The view select resets to the current name, or a neutral "—", after every action and cancel. The popout select resets to "off" on a "was open, now closed" transition only.
10. **Capture vs deck.** While a deck plays and a capture is live, the card shows "visuals: ‹source›, not the deck". No bpm/key is shown for a capture.
11. **Settle state** is visible next to Build whenever it is on.
12. **Persistence is stated.** keep-duplicates is persisted. settle is "this session only" (recommended; see §8). register colour is persisted or marked session-only.

1. **The Play/Pause merge would lose Pause if implemented literally.**

[check-panels.js:537](C:/Claude/Code/Deckwave/tools/check-panels.js:537)

2. **The primary-action table is incomplete, and corpus emptiness is the wrong top-level discriminator.**
