# Getting a Browser-Based DJ App onto iOS and Android: Delivery Routes, Blockers, and a Recommended Architecture

> **Researched August 2026.** Third-party versions, terms, prices, quotas
> and browser-support claims below are as of that date and are NOT
> maintained. Re-check anything you intend to rely on.


## TL;DR
- **The single decisive constraint is not licensing alone but iOS file access plus the AGPL store conflict — and both point to the same answer: build a desktop "analyser" plus a thin mobile "companion player," and distribute the mobile companion natively.** The full analyse-in-browser app cannot be faithfully reproduced on an iPhone because iOS Safari cannot use `showDirectoryPicker`, cannot reliably play audio when backgrounded/locked, and will kill a tab that decodes a whole FLAC library into memory.
- **The AGPL-3.0 dependency on Essentia.js is a hard blocker for the Apple App Store and a soft-to-hard blocker for Google Play; a PWA sidesteps stores entirely but inherits iOS's background-audio and file limits.** Buying a commercial Essentia licence from MTG-UPF and relicensing clears the copyleft path (SoundTouchJS is MPL-2.0 and libFLAC is BSD, both store-safe), but does not fix the iOS technical limits.
- **The companion model is proven in DJ software (rekordbox Cloud Analysis, Lexicon DJ Mobile) and avoids the memory and file problems because the phone only ever holds one or two tracks.** Rank order: (1) desktop analyser stays a PWA/desktop app + native companion player on mobile; (2) Capacitor wrapper of a slimmed player; (3) full PWA; (4) full native rewrite. A verbatim port of today's app to a phone is a dead end.

## Key Findings

**1. `<input webkitdirectory>` on iOS: the wrong assumption, now partly corrected.** For years iOS Safari silently ignored `webkitdirectory` — the attribute reflected but the picker only ever returned single files. WebKit bug 271705 was fixed and, per Apple engineer Alexey Proskuryakov's comment on that bug, it "should be fixed in iOS 18.4 beta." MDN now lists `webkitdirectory` as Baseline "Newly available" since August 2025. So on **iOS 18.4+** a directory picker works; on iOS 18.3 and earlier it does not. `showDirectoryPicker()` (the File System Access API) is **still not supported at all** on iOS Safari — only OPFS is. This means your desktop `showDirectoryPicker` code has no iOS equivalent; the best you get on a modern iPhone is a one-shot `webkitdirectory` multi-file selection with no persistent handle.

**2. File objects cannot be re-read on a later visit.** On both platforms, a `File` obtained from `<input>` is a snapshot reference; there is no persistent handle (Safari has no `FileSystemFileHandle` persistence, and IndexedDB-stored handles are a Chromium-only feature). To reuse audio across sessions you must **copy bytes into OPFS/IndexedDB**, which reintroduces the storage-quota problem.

**3. OPFS exists on iOS 15.4+ and Android, but quotas and eviction make "copy the whole FLAC library onto the phone" unrealistic.** Per the WebKit blog "Updates to Storage Policy": "Starting in Safari 17.0... For a browser app, overall quota is up to 80% of the total disk space." (The older 1 GB starting limit with incremental prompts was removed in iOS 17 — the quota is now calculated from total disk space without asking the user.) The decisive risk is eviction: per MDN/WebKit's "Storage quotas and eviction criteria," "If an origin has no user interaction, such as click or tap, in the last seven days of browser use, its data created from script will be deleted... This eviction policy does not apply to installed PWAs that have been added to the home screen." `navigator.storage.persist()` on Safari therefore only meaningfully protects an installed Home Screen web app. So a multi-gigabyte FLAC copy is technically permitted but fragile, slow, and duplicates the user's library.

**4. Memory: decoding a whole library will crash the tab.** A 5-minute stereo file decoded via `decodeAudioData` is ~100MB of float PCM. Per-tab memory ceilings on iOS are low and undocumented; community measurements put older iPhones around 1–2GB before the tab is jettisoned, and Safari additionally caps total canvas memory (the "Total canvas memory use exceeds the maximum limit" error). Your existing analyse-then-discard model (decode → measure 120s → release the AudioBuffer) is exactly the right mitigation and is the reason the desktop app is memory-safe; a naive port that holds several decoded tracks at once will not survive. Per WebKit's "Features in Safari 26.0," "Safari 26.0 expands support for WebCodecs API by adding AudioEncoder and AudioDecoder" — Safari 16.4–18.7 shipped only the video interfaces, with `AudioDecoder` undefined. So WebCodecs partial/streaming audio decode is only available on the very newest Safari.

**5. Background audio is the iOS killer.** Web Audio and even `<audio>` playback in iOS Safari/WKWebView is suspended when the screen locks or the app is backgrounded — this is a longstanding WebKit limitation (bugs 198277, 211018) with active developer complaints in 2024–2025. The Media Session API (lock-screen metadata/controls) is supported on iOS Safari 16.4+ but does not by itself keep Web Audio running when locked. **A DJ set that stops when the phone locks is unacceptable, and there is no pure-web fix on iOS.** Android Chrome fares better but a Capacitor/Cordova WebView on Android also sleeps unless a native foreground-service plugin is used.

**6. AudioWorklet + 12 canvases at 60fps is unrealistic on a phone without degradation.** The Web Audio WG's own issue tracker (issue #2632) documents AudioWorklet producing distortion/crackle on mobile Chrome and iOS "across all mobile devices and browsers" under load. Your SoundTouchJS time-stretch AudioWorklet is feasible, but twelve simultaneous 60fps canvas panels driven from an AnalyserNode will need to degrade (fewer panels, lower frame rate, or `OffscreenCanvas` in a worker).

**7. The AGPL/App Store conflict is real, specific, and still current.** Apple removed GNU Go (2010) and VLC (2011, again 2014) after FSF complaints. Per The Register (May 27, 2010), "Apple removed an iPhone port of GNU Go from the App Store after receiving a letter from the Free Software Foundation," the sticking point being that the store terms say software "can only be used on five devices." The FSF's analysis, written by Licensing Compliance Engineer Brett Smith in "More about the App Store GPL Enforcement," is precise: Apple's "Rules (i) and (iii) say that you are required to accept the Terms of Service to use the software, and that you may only install the software on five approved devices... exactly the kind of 'further restrictions' that are prohibited by the GPL," and he adds that "this analysis would apply to all versions of the GNU GPL and AGPL." Apple's current Licensed Application EULA still says "you may not distribute or make the Licensed Application available over a network where it could be used by multiple devices at the same time" and "you may not transfer, redistribute or sublicense." Because Essentia.js is AGPL-3.0, a combined work is AGPL, so this conflict applies. GPL apps have shipped only when the copyright holder grants an exception or dual-licenses.

**8. Google Play is more permissive but not clean.** Google Play has hosted GPL apps; the conflict is milder because Play's terms are less restrictive than Apple's device-count rule. The bigger 2025–2026 wrinkle is Google's developer-registration decree: F-Droid board member Marc Prud'hommeaux, in F-Droid's Sept 29, 2025 post, warned that "if it were to be put into effect, the developer registration decree will end the F-Droid project and other free/open-source app distribution sources as we know them today." The requirement rolls out in phases beginning around September 2026.

**9. F-Droid accepts wrapped web apps and copyleft software, but its future is uncertain.** F-Droid's Inclusion Policy requires all apps be FLOSS (GPL/Apache etc.), forbids proprietary trackers (Firebase/Crashlytics/ad SDKs), and builds from source. WebView wrapper apps are accepted (e.g., CanIWebView, gptAssist). AGPL is fine. But Google's registration rules threaten F-Droid's reach on certified Android devices.

**10. The DMA lets a non-EU developer reach EU iOS users via alternative app stores — but only under Apple's alternative terms, which trigger the Core Technology Fee.** As of 2026, AltStore PAL, Epic Games Store, Aptoide, and Onside operate in the EU (and now Japan). Apps must still be notarized by Apple. Opting into alternative distribution puts you on Apple's alternative business terms, where the CTF applies. Per Apple's "Core Technology Fee" support page, Apple Developer Program membership "includes one million first annual installs per year for free," and "developers pay a CTF of €0.50 for each first annual install over one million in the past 12 months," with nonprofits and fee-waiver government/education entities and no-revenue free apps exempt. So a solo developer well under 1M installs pays no CTF. This is the one route that could put an AGPL app "app-store-like" onto EU iPhones, because AltStore PAL is built precisely for open-source/sideloaded apps.

**11. The companion model has strong precedent.** rekordbox's "Cloud Analysis" downloads precomputed BPM, beatgrid, waveform and vocal position; "CloudDirectPlay" lets a CDJ-3000 play from the cloud with analysis fetched, not recomputed (Pioneer DJ News, 2023). Lexicon DJ ships a WebView-based mobile companion (iOS + Android) that pulls precomputed waveforms, cues, loops and beatgrids from the desktop library and does not re-analyse on the phone. Algoriddim djay, by contrast, syncs only user-generated cue points and loops via iCloud — its support docs state "BPM analysis data cannot be synced," so each device re-analyses BPM/beatgrid/waveform independently. This confirms your instinct: the ~26KB JSON score is functionally identical to rekordbox's exported analysis — analyse on desktop, play from precomputed data on mobile.

## Details

### Part 1 — The PWA route (verdict: viable on Android, crippled on iOS)

- **(a) Installability & background audio.** Both platforms support Add to Home Screen and service workers (iOS since 11.3; push since 16.4 outside the EU). Media Session works on iOS 16.4+ for lock-screen metadata/controls. The fatal gap is that iOS suspends Web Audio when locked/backgrounded; there is no Wake Lock or background-audio web API on iOS Safari that keeps an AudioWorklet running (Wake Lock itself is unsupported on iOS Safari). Android Chrome keeps audio alive better but a home-screen PWA can still be throttled. **AudioContext starts suspended on both platforms and must be resumed inside a user gesture** — your first play must be behind a tap.
- **(b) File access.** iOS 18.4+ gains `webkitdirectory`; earlier iOS does not, and `showDirectoryPicker` is unsupported on all iOS. `<input multiple>` works to select many files from the iOS Files app and Android's document picker. There is no reliable documented cap on selection count, but large selections are memory-heavy and File objects are non-persistent — you must copy into storage to reuse them.
- **(c) OPFS/persistence.** Available iOS 15.4+/Android. Quotas are generous on paper (WebKit: up to 80% of disk for a browser app) but Safari evicts non-installed origins after 7 days of no interaction; `persist()` is effectively Home-Screen-app-only on Safari. Copying a multi-GB FLAC library is not realistic UX.
- **(d) Memory.** ~100MB/track decoded; iOS tab ceilings are low; analyse-then-discard is essential. WebCodecs `AudioDecoder` for partial decode is iOS-only from Safari 26.
- **(e) Performance.** SoundTouchJS AudioWorklet is feasible but glitch-prone under mobile load; 12×60fps canvases must degrade.

### Part 2 — Native and hybrid wrappers

- **(a) Capacitor (Ionic).** Wraps an existing web app with minimal change; the web code runs in WKWebView (iOS) / Android System WebView. Web Audio/AudioWorklet work but inherit WebView quirks — documented iOS first-play stutter (AVAudioSession activation timing) and Android background-audio suspension unless a native media-session/foreground-service plugin (e.g., `capacitor-media-session`) is added. Capacitor's Filesystem plugin grants real native file access, which is the main reason to wrap: it solves the iOS folder-picking and persistence problems the PWA cannot.
- **(b) Cordova / Tauri 2.0 / others.** Cordova is mature but legacy; same WebView audio constraints, plus higher-memory persistent storage. Tauri 2.0 (stable Oct 2024) supports iOS/Android via WRY→WKWebView/Android System WebView; developers report passing App Store review with Tauri WebView apps, and a `tauri-plugin-native-audio` provides background playback + lock-screen controls via AVAudioSession/MediaPlayer. Tauri is leaner but its mobile developer experience is younger than Capacitor's.
- **(c) React Native / Flutter + WebView.** A WebView inside RN/Flutter runs the same system WebView and inherits every Web Audio limitation, while adding a second framework — worst of both worlds for an audio-heavy app. Not recommended.
- **(d) Full native rewrite.** Essentia has a C++ core and cross-compiles to iOS/Android (it is designed for "industrial applications" and mobile/IoT targets); SoundTouch is C++/LGPL and builds natively; the Web Audio graph maps to AVAudioEngine (iOS) and Oboe/AAudio (Android). This is the most robust but discards nearly all the web codebase.
- **(e) Code survival:** PWA ~100%; Capacitor wrapper ~85–95% (swap file access + audio-session/background plugins); Tauri ~85–90%; RN/Flutter+WebView ~70% (plus new native glue); full native rewrite ~5–10% (only algorithms/score format survive as spec).

### Part 3 — App Store policy and the AGPL problem

- **(a) Apple.** The GPL/AGPL conflict is about the EULA's Usage Rules (mandatory ToS acceptance + the five-device install limit) constituting "further restrictions," per the FSF, and it explicitly applies to AGPL-3.0. GPL apps ship only via a copyright-holder exception. Because you are the app author but not the Essentia copyright holder, you cannot grant that exception for Essentia — only MTG-UPF can (via the commercial licence).
- **(b) Google Play.** More permissive; GPL apps exist; still messy under the new registration decree.
- **(c) F-Droid.** Accepts AGPL and WebView wrappers; forbids proprietary SDKs; builds from source. Reach is modest and now threatened by Google's registration rules.
- **(d) If the app stays AGPL:** realistic channels are PWA (no store), F-Droid + direct APK sideloading on Android, and AltStore PAL / alternative EU marketplaces on iOS under the DMA (notarization required, CTF waived for a solo developer under 1M installs).
- **(e) If a commercial Essentia licence is bought and the app relicensed:** the copyleft blocker clears. Remaining deps are store-safe — SoundTouchJS is MPL-2.0 (file-level copyleft, App-Store-compatible) and libFLAC is BSD. So relicensing clears the *legal* store path entirely; it does **not** fix the iOS technical limits.
- **(f) Guideline 4.2/4.7.** A bare WebView that only loads the app would risk 4.2 "repackaged website" rejection ("Your app should include features, content, and UI that elevate it beyond a repackaged website"). But a real DJ engine with native file import, background audio, and lock-screen controls is well beyond "minimum functionality"; wrapped apps with genuine native integration (Amazon, Instagram, Basecamp use WebViews) pass routinely. The risk is manageable if you add native value, not fatal.

### Part 4 — The companion model (the actual answer)

- **(a) Viable.** The phone reads the 26KB score, locates the referenced audio files, and plays them beat-locked with SoundTouch time-stretch — holding only the current and next track in memory.
- **(b) Getting files to the phone.** Options: files already in device music storage (imported once via native picker), cloud (iCloud/Google Drive), direct transfer, or streaming from the desktop over the LAN. rekordbox uses USB export and cloud; Lexicon uses desktop→mobile sync.
- **(c) Precedent.** rekordbox Cloud Analysis/CloudDirectPlay and Lexicon DJ Mobile both precompute on desktop and play from precomputed analysis; the CDJ-3000 "instantly acquires BPM, beatgrid and waveform" from the cloud rather than re-analysing. djay syncs only cues/loops via iCloud and re-analyses BPM per device. Notably, Lexicon DJ Mobile is itself a WebView-based hybrid shipped to both the App Store and Google Play — the closest positive precedent for a wrapped web DJ tool.
- **(d) Avoids memory and file problems.** Yes — one or two tracks in memory means no OOM; a single native import solves file access; no multi-GB OPFS copy.

### Part 5 — Ranking (see Recommendations)

## Recommendations

**Stage 1 — Decide the licence first, because it gates everything.** If reaching the Apple App Store natively matters, budget for a commercial Essentia licence from MTG-UPF and relicense the app; then SoundTouchJS (MPL-2.0) and libFLAC (BSD) are store-safe. If you will not pay for Essentia, accept that the iOS App Store is closed and plan for PWA + F-Droid/APK + AltStore PAL (EU).

**Stage 2 — Split the architecture.** Keep the analyser as it is (desktop Chromium / PWA), where `showDirectoryPicker`, memory headroom and analyse-then-discard already work. Build a **thin companion player** for mobile that consumes the score + audio and holds ≤2 decoded tracks. This is the highest-leverage decision: it removes the three worst mobile constraints (file access, memory, background audio) at once and mirrors how rekordbox and Lexicon already operate.

**Stage 3 — Wrap the companion with Capacitor** (first choice) for real native file access (Filesystem plugin), background audio (media-session/foreground-service plugin), and lock-screen controls, preserving ~85–95% of the player web code. Tauri 2.0 is a viable leaner alternative if you want a Rust native layer and its `native-audio` plugin. Ship Android to Play/F-Droid and, if relicensed, iOS to the App Store; if not relicensed, iOS via AltStore PAL in the EU.

**Dead ends to avoid:** (a) a verbatim port of the full analyse-in-browser app to iOS Safari — folder picking, background audio and memory all break; (b) copying a multi-GB FLAC library into OPFS on a phone; (c) shipping the AGPL app to the Apple App Store without relicensing; (d) RN/Flutter+WebView, which adds a framework without fixing Web Audio.

**Benchmarks that change the plan:** If Apple ships background Web Audio (watch WebKit bugs 198277/211018) and persistent file handles, a full PWA becomes viable on iOS and Stage 3 can be dropped. If Google's registration decree (phasing in from ~September 2026) kills F-Droid, fall back to direct APK + Play. If the EU CTF's 1M-install waiver is removed, AltStore economics change. If you cross ~1M EU installs, reassess CTF exposure.

## Caveats
- The exact iOS per-tab memory ceiling is undocumented; figures cited are community measurements, not Apple specs. Test on target hardware.
- "iOS 18.4 fixes webkitdirectory" is from a WebKit engineer's Bugzilla comment; confirm on your minimum-supported iOS version before relying on it.
- The Serato "no first-party mobile companion in 2026" finding rests partly on a third-party guide plus the absence of any first-party product; treat as medium confidence. Serato Remote/Remote Mini are discontinued (legacy iOS only).
- DMA/CTF rules and Google's registration decree are both in flux in 2026; verify current terms before committing.
- No named example of a *pure-Essentia* DJ app on either store was verified, nor a documented web-DJ-app store *failure*; Lexicon DJ Mobile is the closest positive precedent for a shipped web-wrapped DJ tool.
- SoundTouchJS licence: current releases are MPL-2.0, but verify the specific version you bundle, as older forks used LGPL.
