# Browser-Based Automatic DJ & Reactive Music: Beat-Lock, Set Construction, Sonification, and Export

> **Researched August 2026.** Third-party versions, terms, prices, quotas
> and browser-support claims below are as of that date and are NOT
> maintained. Re-check anything you intend to rely on.


## TL;DR
- **Beat-lock is solvable today in a no-build script**: route each deck's AudioBuffer through a SoundTouchJS AudioWorklet for realtime pitch-preserving time-stretch; exact rate-matching plus periodic phase re-anchoring on downbeats eliminates the 12-second drift. Rubber Band R3 WASM is higher quality but roughly 3× the CPU of R2 and marginal for two simultaneous live decks; reserve it for the offline FLAC render.
- **Automatic set construction has a mature, evaluated literature to copy directly**: Foote novelty on beat-synchronous SSMs (8-bar kernel) for structure, Zehren et al.'s three-rule switch-point method (96% good cue points), Bittner et al.'s graph/Hamiltonian-path sequencing, and Camelot+tempo+energy+timbre scoring — all implementable in JS.
- **Sonification should borrow from adaptive game music, not alarms**: use vertical layering for continuous energy, reserve distinct earcons for rare events (errors, prompt-injection), quantize every event-driven change to the next beat/bar (a 500 ms / 2000 ms budget at 120 BPM), and schedule with Chris Wilson's 25 ms/100 ms lookahead pattern to avoid habituation and stay musical.

## Key Findings

**Part 1 — Beat-lock and time-stretch.** SoundTouchJS ships a maintained AudioWorklet package (`@soundtouchjs/audio-worklet`) whose `SoundTouchNode` extends `AudioWorkletNode`, exposing `pitch`, `pitchSemitones` and `playbackRate` as AudioParams and a static `register()` that wraps `audioWorklet.addModule()`. It is fed from an AudioBuffer (not a media element), runs off the main thread, and provides `processOffline()` for the render path. Its WSOLA time-domain algorithm is CPU-light and comfortably runs multiple decks. Rubber Band's WASM builds (Daninet/rubberband-wasm, delude88/rubberband-web) offer far higher quality, but the R3 engine is ~3× the CPU cost of R2 and GPL (commercial use needs a licence). Exact rate-matching is necessary but not sufficient over minutes; residual beat-grid and floating-point error makes decks drift ("double bass kick"), so DJ tools (Mixxx Sync Lock, Traktor, Rekordbox) continuously re-align phase to a leader clock. Perceptual limit: ±15% tempo change is the practical clean-quality boundary; beyond ~±25% music "sounds awkward."

**Part 2 — Set construction.** The canonical structure detector is Foote's checkerboard-kernel novelty over a self-similarity matrix. Zehren/Alunno/Bientinesi (ISMIR 2020 / Computer Music Journal 2022) give a directly implementable three-rule pipeline (novelty → period selection at 4-bar multiples → salience) yielding ~96% usable switch points, with open-source code (MZehren/Automix) and dataset (M-DJCUE). Vande Veire & De Bie (EURASIP 2018) is the first full open-source auto-DJ. Bittner et al. (ISMIR 2017, Spotify) models sequencing as a shortest-Hamiltonian-path/cycle graph traversal over key/tempo/timbre similarity. Camelot key compatibility, tempo proximity, energy delta and timbral similarity are the standard scoring terms.

**Part 3 — Sonification.** The auditory-display literature distinguishes parameter-mapping sonification (continuous, learnable, best for energy/progress), earcons (abstract, must be learned, good for discrete rare events), and auditory icons (iconic, low learning cost). Continuous alarms cause habituation and alarm fatigue; adaptive game music (vertical layering + horizontal re-sequencing, FMOD/Wwise) is the better model, transitioning on musical boundaries. Events must be quantized to the next beat/bar. There is a small but real literature on sonifying software/system activity (CAITLIN, Peep network auralizer, and a 2026 EDM-inspired supercomputer sonification paper).

**Part 4 — Export.** The `.cue` sheet format and FLAC's native CUESHEET metadata block (xiph.org spec) both express track offsets; for non-CD-DA, the lead-out track number is 255 and offsets are in samples. OfflineAudioContext allocates the entire output buffer up front, so long mixes must be rendered in segments and concatenated. EBU R128 (−23 LUFS broadcast; streaming targets ~−14 LUFS) defines the loudness target; libebur128-derived and JS implementations exist.

## Details

### PART 1 — TRUE BEAT-LOCK AND TIME-STRETCH

**(a) SoundTouchJS AudioWorklet — API, latency, CPU, feeding from an AudioBuffer.**
SoundTouchJS has been rewritten as an Nx monorepo; the realtime piece is `@soundtouchjs/audio-worklet`, which supersedes the deprecated standalone `soundtouchjs-audio-worklet` repo. The main-thread class `SoundTouchNode extends AudioWorkletNode` and exposes typed AudioParam accessors for `pitch`, `pitchSemitones` and `playbackRate`; a static `register()` handles `audioContext.audioWorklet.addModule()`. Crucially for your use case, it is designed to be **fed from a decoded AudioBuffer**, not a MediaElement: you hand it the buffer and it processes on the audio render thread. There is an important memory caveat — because of the stretch and rate-transposition stages, "it is currently necessary to maintain copies of the AudioBuffer in both the browser's main process thread as well as in the AudioWorkletGlobalScope," so budget ~2× buffer memory per deck. A newer detail: setting `playbackRate` on the node to match the source node's `playbackRate` makes the processor auto-divide pitch so you never manually compensate for rate-induced pitch shift; and `setStretchParameters()` exposes `sequenceMs`, `seekWindowMs`, `overlapMs`, and `quickSeek` for tuning WSOLA at runtime. For the offline render, `processOffline({input, processorUrl, pitchSemitones, playbackRate, stretchParameters})` returns an AudioBuffer with output length ≈ `ceil(input.length / playbackRate)`. Latency: AudioWorklet processes in fixed 128-sample quanta (~2.9 ms at 44.1 kHz), and WSOLA adds a processing window on top (tunable via `sequenceMs`/`overlapMs`, typically ~20–50 ms). CPU: SoundTouch is a time-domain method with "acceptable CPU load … can work real-time on a mobile device," so two decks on desktop Chrome is not a concern.

**No-build-step note:** the worklet processor file must be served with a `text/javascript` or `application/javascript` Content-Type and loaded via `addModule()` with a URL; you can import the node from a CDN as an ES module (`import … from 'https://cdn.skypack.dev/@soundtouchjs/audio-worklet'`). This works without a bundler, but the processor script itself must be reachable as a standalone URL — that is the one wrinkle for a pure no-build deployment.

**(b) Rubber Band WASM — quality vs. realistic CPU for two decks.**
Rubber Band is the recognized higher-quality option ("audio quality is great … handles transients well … reducing phasiness"). WASM builds exist: `Daninet/rubberband-wasm` (low-level) and `delude88/rubberband-web`, the latter shipping a ready-to-use AudioWorklet via `createRubberBandRealtimeNode(audioCtx, processorUrl)` with `setPitch()`, `setTempo()`, `setHighQuality()`. The key cost fact is from Rubber Band author **Chris Cannam (The Breakfast Post, 30 September 2022)**: version 3.0 introduced the R3 engine, and while "the output of R3 typically sounds much better than R2, it uses a lot more CPU power to run… we find R2 to be typically about three times as fast as R3." Both are "eminently usable in real-time on hardware from the last decade," but the headroom matters. **Realistic recommendation:** R2 (or R3 with care) is feasible for two simultaneous decks on a modern desktop, but WASM + the required buffer copies + two instances is the heaviest configuration you will run. Rubber Band is GPL — commercial redistribution needs a paid licence. The pragmatic split most consistent with the evidence: **SoundTouch WSOLA for live monitoring/preview (cheap, robust), Rubber Band R3 for the offline FLAC render (quality, CPU irrelevant offline).**

**(c) Keeping two decks phase-locked over minutes.**
Exact rate matching is necessary but **not sufficient**. The Mixxx manual is explicit: "A 'perfect' beatmatch is nearly impossible — there will always be a tiny difference in the playback rates," producing the characteristic "double bass kick" as kicks drift out of phase. Mixxx's answer is Sync Lock / Master Sync: a leader clock (a deck with a high-quality beatgrid, or an internal/external clock) to which followers continuously align tempo *and* phase, with "quantize" snapping adjustments to the beat. Mixxx's own bug history (#10024 "Changing the tempo of two master synced tracks causes drifting," #15600 drift on beatgrid edits) shows even mature implementations need active correction, not one-shot matching. **Concrete design:** (1) compute the exact rate ratio to a common target BPM; (2) because `AudioBufferSourceNode.start(when, offset)` and time-stretch introduce accumulating sample error, re-anchor phase every N downbeats by nudging one deck's playback position (or scheduling the next loop/segment) to the leader's downbeat time derived from `AudioContext.currentTime`. In practice, re-anchoring at each 8- or 16-bar phrase boundary (where you are usually making structural moves anyway) keeps drift below the audible threshold without artefacts.

**(d) Common target BPM for the whole set vs. stretch only during transitions.**
- *Stretch only during transitions:* each track plays at native tempo except during the blend, where the incoming (or outgoing) track is ramped to a shared tempo. Minimizes total time-stretch exposure and artefacts, but requires a smooth tempo ramp and means the two tracks are only rate-matched for the overlap — good for short blends, harder for long 12-second-plus blends because you must ramp tempo while also aligning phase.
- *Common target BPM for the set:* every track is stretched to one tempo, so decks are always rate-locked and phase-lock is trivial (only re-anchoring needed). Cost: tracks far from the target BPM suffer more artefacts and may cross the perceptual limit. **Recommendation:** pick a target BPM per *segment* of the set (a slowly moving target that tracks the energy arc), keep each track within ±6% of its native tempo where possible, and only exceed that for deliberate effect. This mirrors how the tempo-matching literature constrains selection (see (e)).

**(e) Perceptual limits of tempo change.**
Multiple independent sources converge on **±15% as the clean boundary**: a time-stretch calculator's rule of thumb ("staying within ±15% of the original tempo produces clean results; beyond that, artifacts become more noticeable"), and a Philips patent on tempo-matched exercise music states music stretched "more than 125%" sounds awkward and uses scaling factors of −15% to +25%. This directly constrains set construction: **candidate next tracks should sit within roughly ±6% of the current target for inaudible stretching, tolerate up to ±15% for a strong musical reason, and be excluded beyond that.** This is exactly the constraint Vande Veire/AutoMashUpper encode — the next track is chosen partly because its native tempo is close to the desired tempo. Note the interaction with key: pitch-preserving stretch avoids the key change that naive resampling would cause, so tempo and key can be treated as independent scoring axes.

**(f) HPSS for differential stretching (Driedger & Müller) and JS/WASM availability.**
Driedger, Müller & Ewert, "Improving Time-Scale Modification of Music Signals Using Harmonic-Percussive Separation" (IEEE Signal Processing Letters 21(1):105–109, 2014) is the reference: split the signal into harmonic and percussive components (median filtering across time vs. frequency, per Fitzgerald 2010 / Driedger-Müller-Disch ISMIR 2014), then **stretch the harmonic part with a phase vocoder and the percussive part with WSOLA**, and sum — preserving both transient sharpness and harmonic quality. Reference implementations exist in MATLAB (AudioLabs TSM Toolbox, MIT-licensed), Python (librosa `effects.hpss`, nussl), but **there is no established, maintained pure-JS/WASM HPSS+TSM library**. This is the one Part-1 capability that is *untested* in-browser: you would have to port median-filter HPSS to JS/WASM yourself (feasible — it is FFT + median filtering) or run it only in the offline render via a WASM FFT. For live use, SoundTouch/Rubber Band's built-in transient handling is the practical substitute; HPSS-differential stretching is a quality upgrade best reserved for the offline render.

### PART 2 — AUTOMATIC SET CONSTRUCTION AND MIX-POINT SELECTION

**(a) Structure and phrase detection — Foote novelty, kernels, features, snapping.**
Foote's method (ICME 2000): build a self-similarity matrix (SSM) from a feature sequence, correlate a **Gaussian-tapered checkerboard kernel** along the main diagonal to produce a novelty curve, and peak-pick. The essential engineering choices, drawn from the working literature:
- **Features:** MFCC/CQT for timbre, chroma/PCP for harmony; the standard is to compute several and combine. Zehren et al. use seven: kick/snare/hi-hat onset densities (drum transcription), CQT (84 bins, f₀=32.7 Hz, hop 512), and PCP (7 octaves, f₀=27.5 Hz), plus separate harmonic/percussive energy from librosa HPSS.
- **Beat-synchronous aggregation:** aggregate features to the beat (or strong-beat) grid before building the SSM — this gives tempo invariance and is what makes downbeat snapping natural. Zehren quantize to "strong beats" (beats 1 and 3) and aggregate by RMS (or onset count for sparse drum features).
- **Kernel size:** set it to the musical unit you care about. Zehren compute novelty between **4-bar segments, i.e. an 8-bar kernel** — "corresponding to the typical smallest length of a section." For finer boundaries, use Kaiser & Peeters-style multi-scale kernels. (Note: absolute kernel size in frames must be small relative to the SSM; oversized kernels only slide over a tiny diagonal region and produce degenerate novelty.)
- **Distance:** standardized-Euclidean (Zehren) or cosine (Foote/Jipes default).
- **Snapping:** enforce that boundaries land on downbeats and on **4-bar (period) multiples**; detect the period phase offset by choosing the offset (of 8 candidates) that maximizes total novelty (Vande Veire's method as modified by Zehren). EDM is "invariably in 4/4," built from repetitions of 2 (or multiples of 2) bars, so "every period of four bars anticipates the potential start of a new music section."

**(b) Published auto-DJ systems and their evaluation.**
- **Vande Veire & De Bie, EURASIP J. Audio Speech Music Proc. 2018:13** — "From raw audio to a seamless mix: creating an automated DJ system for Drum and Bass." First fully-integrated open-source auto-DJ: beat/downbeat tracking, structural segmentation, cue-point identification, cross-fade profile selection, and playlist compilation, using Foote novelty improved with genre rules. Positively evaluated but not extended beyond DnB.
- **Zehren, Alunno & Bientinesi** — ISMIR 2020 ("Automatic Detection of Cue Points for DJ Mixing," arXiv 2007.08411) and the extended Computer Music Journal 46(3):67–82, 2022. Three rules: **Rule 1 Novelty** (switch point marks high novelty in rhythmic density, loudness, timbre and/or harmony); **Rule 2 Section detection** (switch point always on the downbeat at the start of a 4-bar period); **Rule 3 Salience** (the section after the switch must "stand on its own" — implemented as harmonic energy above 0.4× the track max over the following 4 bars). Evaluation: 134-track expert-annotated EDM dataset (M-DJCUE, tempo 99–147 BPM), hit = within 0.5 s of an annotation. The ISMIR 2020 paper states verbatim: "We found that about 96% of the points generated by our methodology are of good quality for use in a DJ mix"; the CMJ 2022 two-method version reports "about 90 percent." Code: github.com/MZehren/Automix. Follow-ups: "Cue Point Estimation using Object Detection" and Zehren et al., "Interpretability of Methods for Switch Point Detection," *Signals* 5(4):642–658, 2024.
- **Davies, Hamel, Yoshii & Goto, AutoMashUpper (TASLP 22(12):1726–1737, 2014; ISMIR 2013)** — phrase-level segmentation (Foote) then a "mashability" score = weighted sum of harmonic similarity (beat-synchronous chromagrams), rhythmic similarity, and spectral balance, computed over user-defined key-shift and tempo ranges. Establishes that compatibility should be measured *after* the transposition/stretch you intend to apply, not on raw features.
- **Bittner et al., "Automatic Playlist Sequencing and Transitions," ISMIR 2017** (Spotify) — sequencing as **graph traversal**: songs are vertices weighted by acoustic/musical similarity; solve for a shortest Hamiltonian path (greedy) or Hamiltonian cycle (TSP 2-approximation) for a loopable set; key/mode mapped into 3-D Euclidean space; crossfade as an optimization. Subjectively evaluated by professional curators.
- **Earlier/related:** Cliff "Hang the DJ" (HP Labs 2000, transition during beatless breakdowns); Kim et al. "highlight detection" (ISMIR 2017 LBD); Schwarz, Schindler & Spadavecchia heuristic cue-point (SMC 2018); Kell & Tzanetakis (ISMIR 2013, empirical track ordering); Kim et al. mix-to-track subsequence alignment (ISMIR 2020). **More recent (to 2026):** GAN-based "Automatic DJ Transitions with Differentiable Audio Effects and GANs" (arXiv 2110.06525), and "DJ AI: Optimizing Playlist Alignment and Generating Transitions with Generative and Embedding Models" (Audio Mostly 2025) which explicitly builds on Bittner's graph formulation.

**(c) Energy-curve / set-arc modelling.**
DJs structure a set as a deliberate energy arc (build → peak → release). The composite energy index you already store is the right primitive. The strongest *quantified* handle in the literature is intensity/loudness curves and the "drop/breakdown/riser" vocabulary from EDM structure analysis (Zehren) rather than a single published canonical arc function — treat the arc as a target energy trajectory you fit the sequence to (e.g., a smooth rise to ~70% of the set then a peak), and penalize next-track choices whose energy deviates from the trajectory. This is *common practice* rather than a strongly-evaluated formula; flag it as such.

**(d) Next-track scoring function.**
Combine, as a weighted sum (the AutoMashUpper/Bittner pattern), normalized to [0,1]:
- **Key compatibility (Camelot):** same key, ±1 on the wheel (adjacent number), or relative major/minor (same number, switch letter) score high; distant keys score low. Vande Veire uses circle-of-fifths allowed changes.
- **Tempo proximity:** favor candidates whose native tempo is within the ±6%/±15% stretch budget of the current target (Part 1e).
- **Energy delta:** small, arc-consistent steps preferred (Part 2c).
- **Timbral similarity:** MFCC-based distance (Bittner's timbral continuity term).
There is **no single universally-published weighting**; each system tunes its own. Bittner learns edge weights from listener data; AutoMashUpper exposes weights to the user. **Recommendation:** start with equal weights, then bias toward key + tempo (the hard mixing constraints) over timbre/energy (soft preferences), and expose them as tunable — this matches how the evaluated systems behave.

**(e) Transition-type selection and EQ automation.**
Map transition type to the structural context:
- **Long blend (8–16 bars):** two compatible tracks, both in steady sections; the default for house/techno.
- **Bass swap (three-band EQ):** during the overlap, cut the incoming track's low band and run the outgoing track's bass, then at the downbeat swap — kill outgoing bass, bring in incoming bass. Avoids the muddy "two kicks + two basslines" pile-up. This is the canonical EQ automation and is implementable with three `BiquadFilterNode`s (lowshelf/peaking/highshelf) per deck whose gains are automated with `setValueAtTime`/`linearRampToValueAtTime`.
- **Cut:** hard switch on a downbeat when tracks are tempo- or key-incompatible or for energy jumps.
- **Echo-out:** apply a feedback delay to the outgoing track's tail as it leaves — a `DelayNode` + feedback `GainNode`, ramped up over the last bar.
Vande Veire's system explicitly selects a cross-fade profile per transition; adopt the same "profile per transition, chosen by context" architecture.

**(f) Detecting intro / outro / drop / breakdown.**
Use the same beat-synchronous novelty pipeline plus energy heuristics: **intro/outro** = the first/last sections (often lower harmonic/percussive energy, sparse); **breakdown** = a section where energy (esp. percussive/kick density) drops — Cliff's "Hang the DJ" defines it operationally as where a beat tracker fails; **riser** = rising energy/spectral centroid leading into a **drop** = the first downbeat of a sudden high-energy section (large positive novelty in loudness + percussive density). Zehren's kick/snare/hi-hat onset-density features and harmonic/percussive energy split are exactly what discriminate these. Mix points should land on these structural downbeats: switch-in near the incoming track's first strong core section, switch-out near the outgoing track's outro/breakdown.

### PART 3 — SONIFICATION REACTING TO AGENT ACTIVITY

**(a) Parameter mapping, earcons, auditory icons — what is learnable, what is ignored.**
The Sonification Handbook's five techniques: audification, **parameter-mapping sonification (PMS)**, model-based sonification, **auditory icons**, and **earcons**.
- **PMS** maps data dimensions to auditory dimensions (pitch, loudness, timbre/brightness). It is "the most widely used sonification technique" and communicates continuous information. **Dubus & Bresin, "A Systematic Review of Mapping Strategies for the Sonification of Physical Quantities," PLOS ONE 8(12):e82491, 2013**, reviewed 179 publications and built a database of 495 mapping entries, concluding "pitch is by far the most used auditory dimension in sonification applications." Best for your *continuous* channels: agent "energy," value-of-findings, scan rate → music intensity/brightness/tempo.
- **Earcons** are abstract musical motifs with **purely symbolic mappings that must be learned from scratch**, but are easily parameterized and combined hierarchically. Best for your *discrete rare* events. Learnability research: requiring users to correctly identify each earcon once before use raises recognition to speech-like levels; structured/hierarchical earcons are easier to learn, and users can infer an unheard parameter change from learned structure (Brewster). Identification rates ~90% are achievable with training.
- **Auditory icons** are iconic (real-world sound → analogous event), so they need little learning — good for events with a natural metaphor (e.g., an "error" as a broken/dissonant sound). Spearcons (sped-up speech) are as learnable as speech.
**Design implication:** continuous state → PMS (won't require learning, but is easy to ignore, which is fine for background); rare high-value events (significant find, error, **prompt-injection signature**) → distinct, pre-learned earcons/auditory icons that punch through. Arbitrary earcons with no training will be *ignored*.

**(b) Continuous background sonification for monitoring — vigilance, alarm fatigue, habituation.**
The monitoring literature is a clear warning about the *alarm* framing: frequent auditory warnings cause **habituation** ("decreased neural response to specific repeated stimuli," slower reaction times) and **alarm fatigue** (desensitization, mistrust, delayed/absent response). Two hard datapoints quantify the false-alarm problem: **Drew et al., "Insights into the Problem of Alarm Fatigue…," PLOS ONE 2014**, a 31-day study of 461 UCSF ICU patients, found "88.8% of the 12,671 annotated arrhythmia alarms were false positives" and "93% of the 168 true ventricular tachycardia alarms were not sustained long enough to warrant treatment"; in pediatrics, **Bonafide et al. (CHOP)** per the AAMI review report that up to 99% of monitor alarms "may be unnecessary or 'nuisance'," with a general pediatric unit generating "up to 152 alarms per patient per day" and "as few as 1% of alarms clinically important." But *continuous, non-alarm* sonification can *help*: a business-process monitoring study (SoProMon) found that "a variant combining visualization, auditory alerts and continuous sonification increases monitoring performance significantly over visualization alone." Mitigations from the construction-equipment study (Chae et al., *Automation in Construction* 2024): novel/varied alarm sounds and self-relevant sounds reduce habituation vs. a repeated probe tone. **Design implication:** make the *continuous* layer pleasant and musical (not alarm-like) so it can be tuned out safely; reserve salient, *varied* signatures for genuinely actionable rare events; never fire a hard alarm on routine activity, or the agent's operator will learn to ignore the whole channel.

**(c) Adaptive/generative game music — the closest practical art.**
Two techniques: **vertical remixing/layering** (stack synchronized stems; mute/unmute layers to raise/lower intensity in real time — Red Dead Redemption, Hollow Knight combat) and **horizontal re-sequencing** (branch between loopable sections/segments — DOOM Eternal's tempo-synced chunks jump between Intro/Verse/Bridge "without ever breaking the tempo or the beat"). Middleware (FMOD, Wwise, Elias) maps game state (e.g., a `Threat_Level` RTPC) to these transitions. Best practice from the field: combine both (vertical layering within horizontal groups); plan **cue points, transition windows and fallback loops to avoid abrupt cuts**; use stingers/risers to bridge. **Direct lesson for your system:** model the soundtrack as stems you can fade in/out (vertical: energy) plus a small set of loopable sections you can branch between (horizontal: mode changes — "researching" vs "found something" vs "error"), and transition only at musical boundaries.

**(d) Making event-driven changes land musically — quantization and the latency budget.**
Do **not** fire changes immediately; quantize them to the next beat, bar, or phrase. The perceptual basis:
- **Onset-timing JND:** Friberg & Sundberg (J. Acoust. Soc. Am. 98(5):2524–2531, 1995) — displacing a tone in an isochronous sequence is detectable at **~6 ms for short tones, or ~2.5% of the inter-onset interval for intervals >250 ms**. In richer musical contexts thresholds rise: Ehrlé & Samson (2005) found 16–23 ms anisochrony thresholds; Frane & Shams (2017) 12–16 ms for swing patterns. So scheduling error should stay within ~6–20 ms of the target beat.
- **Action-to-sound latency tolerance:** Jack et al. (Music Perception 36(1):109–128, 2018) found **10 ms latency is acceptable, but 20 ms — or 10±3 ms of jitter — significantly degrades** the experience; Wessel & Wright (2002) recommend ≤10 ms latency and ±1 ms jitter; the ensemble-performance threshold is ~20–30 ms. Comb-filtering/echo effects become problematic around ~10 ms and read as echo by ~30 ms.
- **Beat/bar budget:** at 120 BPM a beat = **500 ms**, a 4/4 bar = **2000 ms** (confirmed in Oore et al., "This Time with Feeling," arXiv 1808.03715). Quantizing to the next beat therefore costs up to 500 ms of latency (up to 2000 ms to the next bar) — perceptually fine for background music and far preferable to an off-beat stab. Choose the grid by urgency: errors/prompt-injection → next beat (fast, still in time); mode/energy shifts → next bar or phrase.
- **Scheduling mechanism:** use Chris Wilson's "A Tale of Two Clocks" pattern — a `setTimeout` loop at a **25 ms interval** that schedules every event due within a **100 ms lookahead** using the sample-accurate `AudioContext.currentTime` clock and `start(when)`. His verbatim guidance: "A good place to start is probably 100ms of 'lookahead' time, with intervals set to 25ms." This tolerates JS main-thread jank while keeping events sample-accurate. Tone.js and WAAClock implement the same pattern. (Note his caveat: a 100 ms lookahead means tempo changes take up to a tenth of a second to take effect — acceptable here.)

**(e) Published work on sonifying software/agent/system activity.**
There is a direct lineage: **CAITLIN** (musical program auralization for debugging — maps language constructs to musical motifs; novices could infer program structure from sound alone, and musical training did not significantly affect performance); **Peep, the Network Auralizer** (WISP — nature sounds like rain/waterfalls mapped to network conditions for ambient monitoring); GitSonifier/SONICSIGHT (sonifying commit/version history — tempo tracks development pace); Berman & Gallagher (Java architecture sonification); Henthorne (Virginia Tech, sonifying performance data for tuning, evaluating perceptual accuracy of mappings). Most relevant and recent: a 2026 arXiv paper, **"Real-time, EDM-inspired sonification of the activity of a supercomputer,"** which explicitly targets *real-time* (not post-mortem trace) sonification, uses EDM as the musical frame, and discusses "aural signatures" for distinct system states and ambient soundscapes for peripheral awareness — essentially your exact design pattern applied to HPC. A robustly-supported takeaway across this literature: **map big/low-value quantities to low pitch and small/high-value to high pitch** (confirmed in pilot studies), and use distinct recognizable signatures for distinct states.

### PART 4 — MIX EXPORT, STRUCTURE AND METADATA

**(a) Cue sheet (.cue) format.**
A `.cue` sheet is a plain-text file (originally CDRWIN) with `FILE`, `TRACK`, `INDEX`, `TITLE`, `PERFORMER` commands; `INDEX 01` marks a track start as `MM:SS:FF` (minutes:seconds:frames, 75 frames/sec). Players that honor cue sheets as playlists/chapter sources for a single long file include **foobar2000 and VLC** (both support WAVE/FLAC/WavPack referenced before a `FILE`), and it is the standard way to describe a continuous DJ mix as separate tracks. Exact Audio Copy produces a relaxed variant that not all players accept. For a browser-generated mix, emitting a `.cue` alongside the audio file is the simplest, most widely-supported tracklist mechanism.

**(b) Chapter markers in FLAC — Vorbis comments and CUESHEET blocks; libflac.js.**
FLAC supports tracklist structure two ways per the xiph.org format spec:
- **CUESHEET metadata block** — a native binary block holding the media catalog number, lead-in samples (0 for non-CD), an `is_cd` flag, and an array of tracks each with a **sample-accurate offset**, a track number (for non-CD-DA the lead-out track number must be **255**; for CD-DA it is 170), ISRC, and index points. This is the "proper" way to embed a tracklist with exact sample offsets. `metaflac --import-cuesheet-from` builds it and adds a SEEKTABLE seekpoint per index (`--export-cuesheet-to` reverses it).
- **VORBIS_COMMENT** — free-form `NAME=VALUE` tags (including a whole cue sheet stored as a `CUESHEET=...` tag via `--set-tag-from-file`), plus a **PICTURE block** for artwork.
**libflac.js caveat (say so explicitly):** libflac.js wraps libFLAC's encoder/decoder and lets you write STREAMINFO and VORBIS_COMMENT/PICTURE metadata, but it does **not** expose a convenient high-level API for authoring the binary CUESHEET block the way `metaflac` or the C `FLAC__metadata_object_cuesheet_*` functions do. In a no-build browser script, the reliable path is: encode the FLAC with libflac.js, embed tracklist + artwork via Vorbis comments and a PICTURE block, and **emit a separate `.cue` file** for chapter/track structure. Writing a spec-conformant CUESHEET block by hand into the FLAC stream is possible but is *untested* in this toolchain — flag it as an implementation risk.

**(c) Embedding tracklist, artwork and per-track metadata in one file.**
Practical stack: a single FLAC with (1) VORBIS_COMMENT holding title/artist/tracklist (and optionally an embedded `CUESHEET=` text tag), (2) a PICTURE block for cover art, and (3) either a native CUESHEET block or an accompanying `.cue` for precise track offsets. MP4/M4A chapters (Nero/QuickTime chapter tracks) are the alternative container if you encode to AAC, but FLAC + `.cue` is the cleaner lossless-DJ-mix convention.

**(d) Rendering very long offline audio — OfflineAudioContext limits, segmentation, gapless join.**
`OfflineAudioContext.startRendering()` "allocates an AudioBuffer large enough to hold the entire rendered WebAudio graph before returning" (MS Edge Explainer). At 48 kHz stereo that is ~700 MB for 80 minutes; multichannel/4-hour renders reach **gigabytes to 11 GB**, and there is **no standard way to stream or chunk the output** (open WebAudio issues #2445/#6/#66; W3C bug 21311). For a 15–60 minute mix, a single OfflineAudioContext render is feasible on a desktop with enough RAM (a 60-min stereo 44.1 kHz render ≈ 1.3 GB of float32), but it is fragile — you cannot cancel it and it can OOM the tab. **Recommendation:** render in **segments** (e.g., per-transition or fixed 1–2 minute windows) and concatenate. To join without a click/gap: render segments with a small **overlap that spans the crossfade**, or ensure each segment boundary falls at a **zero-crossing on a downbeat** and is sample-aligned; concatenate the resulting Float32Arrays contiguously (equal-power crossfade in the overlap region) before encoding. Because your crossfades already happen at downbeats, aligning segment boundaries to those same downbeats makes gapless concatenation straightforward.

**(e) Loudness normalization to target LUFS (EBU R128).**
EBU R128 (built on ITU-R BS.1770) measures **integrated loudness in LUFS** with K-weighting and gating: absolute gate at −70 LUFS, relative gate 10 LU below the ungated mean; momentary = 400 ms window, short-term = 3 s. Broadcast target is **−23 LUFS (±0.5 LU, ±1 LU for live)**, max true peak −1 dBTP. For streaming, **Spotify's own loudness-normalization doc states "We adjust tracks to -14 dB LUFS, according to the ITU 1770 standard"** (with user options Loud −11 LUFS and Quiet −19 LUFS); YouTube, Tidal and Amazon are also ~−14 LUFS while Apple Music targets −16 LUFS. So a DJ mix intended for streaming should aim at roughly −14 LUFS. Measure integrated loudness of the finished render, then apply a single gain offset to hit the target and a true-peak limiter to stay under −1 dBTP. **JS availability:** `libebur128` is the reference C library (compilable to WASM); JS/JSFX ports exist (e.g., AXIA-LUFS uses libebur128; REAPER JSFX R128 meters). There is **no single dominant pure-JS R128 library**, but the algorithm (K-weighting biquads + mean-square + gating) is straightforward to implement with `BiquadFilterNode`/offline analysis, or via a WASM build of libebur128. Flag the WASM/port route as the robust option and a hand-rolled JS implementation as feasible but requiring validation against the EBU test set (Tech 3341).

**(f) DJ-mix-specific export conventions.**
Follow the de-facto conventions: (1) one continuous lossless file (FLAC) + a `.cue` tracklist; (2) embed tracklist and artwork in metadata; (3) normalize to a sensible LUFS target for the destination (−14 LUFS streaming, −23 for broadcast); (4) keep true peak ≤ −1 dBTP; (5) mark track boundaries at the actual switch points (downbeats) so players' next/previous-track navigation lands musically. Optionally embed the per-track BPM/key you already compute into the cue/metadata for downstream DJ tools.

## Recommendations

**Stage 1 — Fix drift (highest priority, fully supported).**
1. Add a SoundTouchJS `@soundtouchjs/audio-worklet` node per deck, fed from your existing AudioBuffers; serve the processor file with the correct Content-Type (the only no-build wrinkle).
2. Rate-match both decks to a common target BPM before the blend; keep each track within ±6% native tempo, allow up to ±15% only deliberately.
3. Implement leader/follower phase re-anchoring at every 8- or 16-bar phrase boundary using `AudioContext.currentTime`-derived downbeat times. **Benchmark:** if you can still hear a "double kick" over a 30-second blend, shorten the re-anchor interval.

**Stage 2 — Automatic set construction (well-evaluated, port existing algorithms).**
1. Implement beat-synchronous Foote novelty (8-bar Gaussian checkerboard kernel, standardized-Euclidean SSM) over CQT + chroma + onset-density features; snap boundaries to 4-bar periods.
2. Implement Zehren's three rules (novelty → period → salience) for switch points; validate against their open M-DJCUE dataset. **Benchmark:** aim for their ~96% usable-cue-point precision on your corpus.
3. Sequence with Bittner's graph approach (shortest Hamiltonian path; cycle if the set should loop), edges weighted by Camelot key + tempo proximity + energy delta + MFCC timbral distance. Start equal-weighted, bias toward key+tempo.
4. Select transition type by structural context; implement the three-band bass-swap with per-deck Biquads and AudioParam ramps.

**Stage 3 — Sonification layer (adaptive-game-music model).**
1. Build a vertical-layering stem engine for continuous state (energy, find-value, scan-rate → intensity/brightness) using PMS; keep it musical and un-alarm-like to avoid habituation.
2. Author a small set of pre-learned earcons/auditory icons for rare actionable events (significant find, error → dissonance, **prompt-injection → a distinct signature**); vary them to resist habituation.
3. Quantize every change to the next beat/bar; schedule with the 25 ms/100 ms two-clock lookahead pattern. **Benchmark:** scheduling error <20 ms from the target beat.

**Stage 4 — Export.**
1. For 15–60 min mixes, render in downbeat-aligned segments and concatenate with equal-power overlaps; only attempt a single OfflineAudioContext render if you have confirmed the tab's memory headroom.
2. Encode FLAC with libflac.js; embed tracklist + artwork via Vorbis comments + PICTURE; emit a companion `.cue`. Treat native CUESHEET-block authoring as optional/experimental.
3. Measure integrated LUFS (WASM libebur128 or validated JS), normalize to −14 LUFS (streaming) or −23 (broadcast), limit true peak to −1 dBTP.

**What would change these recommendations:** if two live Rubber Band R3 decks profile under budget on your target hardware, promote it to the live path; if OfflineAudioContext reliably renders your longest mixes without OOM, skip segmentation; if operators report ignoring event cues, increase earcon variation/salience or move events to a faster quantization grid.

## Caveats
- **No-build-step constraints:** AudioWorklet and libflac.js both require serving separate `.js`/wasm assets at fetchable URLs with correct MIME types; this works without a bundler but is not "single HTML file." SoundTouch's AudioWorklet requires ~2× buffer memory per deck (main thread + worklet scope copies).
- **Untested in this toolchain:** (1) pure-JS/WASM HPSS-differential time-stretch — no maintained library exists; port from the MATLAB TSM Toolbox or run only offline. (2) Authoring FLAC's binary CUESHEET metadata block via libflac.js — not exposed by a high-level API; a companion `.cue` is the safe path. (3) A dominant pure-JS EBU R128 library does not exist; use a WASM libebur128 build or validate a hand-rolled implementation against EBU Tech 3341 test signals.
- **Common practice vs. evaluated:** the set energy-arc as a fitted trajectory, and the exact next-track scoring weights, are common practice and system-specific rather than backed by a single canonical evaluation — tune and A/B them.
- **CPU headroom:** Rubber Band R3 at ~3× R2's cost (per author Chris Cannam), two decks, plus WASM buffer copies, is the heaviest realtime configuration; treat live R3 as conditional on profiling, and prefer SoundTouch live / Rubber Band offline.
- **Perceptual/timing figures** (±15% tempo, 6 ms onset JND, 10–20 ms latency tolerance, 25/100 ms lookahead) are drawn from the cited perception literature (Friberg & Sundberg 1995; Jack et al. 2018; Wilson) and pro-audio sources; they are guidelines, not hard limits, and vary with material and listener expertise.
- **Sourcing note:** the Zehren "~96%" (ISMIR 2020) vs "~90%" (CMJ 2022) figures refer to slightly different method variants; both are reported by the authors.
