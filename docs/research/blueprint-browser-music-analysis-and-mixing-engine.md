# Browser-Based Music Analysis and DJ-Quality Mixing Engine: An Implementation Blueprint

> **Researched August 2026.** Third-party versions, terms, prices, quotas
> and browser-support claims below are as of that date and are NOT
> maintained. Re-check anything you intend to rely on.


## TL;DR
- **Replace the Joe-Sullivan amplitude detector with Essentia.js's `RhythmExtractor2013` (multifeature mode)**, which fuses five onset detection functions and returns beat positions, BPM, and a genuine confidence — it runs in the browser via WASM, loads from a CDN as a plain script (no build step), and works in a Web Worker via the UMD build. This is the single highest-leverage change and directly attacks the low-confidence problem on sidechained/chiptune material.
- **For a several-hundred-track corpus, use `showDirectoryPicker()` + recursive async iteration, analyse a 60–120 s excerpt per track with an analyse-then-discard memory model, persist features (and the directory handle) in IndexedDB, and parallelise decode across Web Workers using WebCodecs `AudioDecoder`.** Never hold more than a few decoded buffers at once.
- **Genuine beatmatching requires per-beat grids + downbeat/phase alignment + pitch-preserving time-stretch.** Schedule beat-locked mixes with `AudioBufferSourceNode.start(when, offset)`, stretch with SoundTouchJS's AudioWorklet build (WSOLA, no build step via CDN), and land transitions on 8/16/32-bar phrase boundaries using Foote novelty segmentation — the approach proven in the Vande Veire & De Bie open-source auto-DJ. Chiptune beat tracking specifically is an unstudied problem; expect to validate empirically.

## Key Findings

**1. The current detector fails for structural reasons, not tuning.** The Sullivan method is an amplitude-domain, single-band (150 Hz lowpass) peak-picker. Its confidence metric (modal inter-peak interval count / total) collapses precisely when (a) sidechain compression smears the kick transient it relies on, and (b) chiptune percussion is square-wave/noise with little sub-bass for the 150 Hz lowpass to isolate. The measured median confidence of 0.096 is consistent with a detector that never locks a stable period. The fix is a **spectral-flux / multi-feature onset detection function**, not a better threshold. Note that the `web-audio-beat-detector` npm package is literally this same Sullivan method ("based on the technique explained by Joe Sullivan") — do not adopt it as a replacement.

**2. Superflux and multi-feature fusion are the right ODFs for this material.** Böck & Widmer's SuperFlux (DAFx-2013, "Maximum Filter Vibrato Suppression for Onset Detection," Maynooth, pp. 55–61) tracks spectral trajectories with a maximum filter over a log-frequency spectrogram. Its headline result — verbatim, "Especially for music with heavy use of vibrato (e.g., sung operas or string performances), the number of false positive detections can be reduced by up to 60% without missing any additional events" — was measured on 25,927 mixed onsets, 7,677 violin onsets and 1,448 operatic-voice onsets. (The 60% figure is specific to vibrato-heavy material, not to loudness fluctuation; but the same max-filter mechanism that suppresses vibrato ripple also lowers the ODF noise floor caused by loudness variation, which is the relevant benefit for sidechained EDM.) SuperFlux is available directly in Essentia as `SuperFluxExtractor`. For tempo/beat, prefer fusion: Essentia's `BeatTrackerMultiFeature` runs beat tracking five times with five different ODFs (complex spectral difference, energy flux, harmonic, sub-band weight, mel auditory) and selects the output by Maximum Mutual Agreement. This redundancy is exactly what rescues material where any single band/feature is weak.

**3. Essentia.js is the correct engine and needs no build step.** It exposes `RhythmExtractor2013` (BPM + beat positions + confidence), `BeatTrackerMultiFeature`, `BeatTrackerDegara`, `PercivalBpmEstimator`, `KeyExtractor` (Temperley/Krumhansl/EDMA profiles), `Danceability`, `LoudnessEBUR128`, and ~200 algorithms total. It loads via `<script>` from a CDN (the WASM `essentia-wasm.web.js` glue + IIFE core) and the UMD build supports Web Workers/AudioWorklets.

**4. Whole-corpus ingestion is solved by the File System Access API on Chromium.** `showDirectoryPicker()` returns a `FileSystemDirectoryHandle` you recurse with `.values()`. Handles are serialisable to IndexedDB; Chrome 122+ supports persistent permission grants. Firefox and Safari do NOT support the disk pickers (only OPFS), so a `webkitdirectory` fallback is mandatory for cross-browser reach.

## Details

### 1. Onset detection function selection for sidechained EDM and chiptune

The published evidence strongly favours spectral over amplitude methods:

- **SuperFlux (Böck & Widmer, DAFx-2013)** is an enhanced spectral flux that uses a maximum filter over a log-frequency (triangular-band) spectrogram to suppress false positives (up to 60% on vibrato-heavy material, as quoted above). Reference implementation is Python (CPJKU/SuperFlux); it is also built into Essentia (`SuperFluxExtractor`, `SuperFluxNovelty`, `SuperFluxPeaks`).
- **Complex-domain** (Bello et al. 2004) combines energy and phase; it is one of the five ODFs fused inside Essentia's multi-feature tracker and is the ODF used by `BeatTrackerDegara`.
- **High-frequency content (HFC)** biases toward percussive/broadband onsets — useful for hi-hats and square-wave clicks but poor for bass-heavy kicks; best used *in combination*.
- **Phase deviation** helps for soft onsets but is noise-sensitive.

For **EDM specifically**, the GiantSteps Tempo dataset — "annotations for 664 2min audio previews from beatport.com" (Knees, Faraldo, Herrera, Vogl, Böck, Hörschläger & Le Goff, "Two data sets for tempo estimation and key detection in electronic dance music annotated from user corrections," ISMIR 2015) — is the reference benchmark. Reported tempo accuracies (Accuracy1 exact / Accuracy2 allowing octave errors, ±4% tolerance) are informative: the Böck RNN tracker scores ~58.9 / 86.4 on GiantSteps; Schreiber ~73.0 / 89.3; and multi-scale CNNs reach ~90.2 / 97.6. The key lesson: even strong trackers show large gaps between Accuracy1 and Accuracy2, meaning **octave/half-double-tempo error is the dominant EDM failure mode** — you must fold to a musically sensible range and, ideally, retain the octave alternatives.

For **chiptune/8-bit/SID/tracker music, there is essentially no published beat-tracking or tempo-estimation literature.** A dedicated search across ISMIR archives, arXiv and the wider web found no paper whose contribution is audio beat tracking on square-wave/noise-percussion chiptune. Adjacent chiptune MIR work is symbolic-domain: YM2413-MDB (Choi et al., ISMIR 2022) is an FM video-game dataset that, for metrical alignment, simply *ran madmom on rendered audio and took the median beat-wise tempo* (verbatim: "we conducted the metrical alignment using the extracted down-beat information of rendered audio files using Madmom … Since most of the pieces had a fixed tempo, we used the median value of the beat-wise estimation of tempo") — with no accuracy evaluation for chiptune; NES-MDB (Donahue et al.) explicitly notes "no tempo or beat information exists in the dataset" and discretises time at a fixed 24 timesteps/second. **Conclusion: chiptune beat tracking is an open problem. Treat any detector's chiptune performance as untested and validate on your own LukHash corpus.** The pragmatic mitigation is (a) a broadband multi-feature ODF (do not rely on a sub-bass band), and (b) confidence-gated fallback.

### 2. Essentia.js and the JS alternatives — a serious evaluation

**Essentia.js (MTG/UPF, AGPLv3), primary source = Correya et al., TISMIR 2021 (DOI 10.5334/tismir.111) + ISMIR 2020 paper:**
- **Algorithms in-browser:** ~200, including the full rhythm suite (`RhythmExtractor2013`, `BeatTrackerMultiFeature`, `BeatTrackerDegara`, `PercivalBpmEstimator`, `BpmHistogramDescriptors`, `SuperFluxExtractor`), `KeyExtractor`, `Danceability`, `LoudnessEBUR128`, spectral features, and TensorFlow.js model inference.
- **Recommended tracker:** MTG explicitly recommends `RhythmExtractor2013`. `multifeature` is slower but more accurate and **returns a confidence value**; `degara` is faster but its confidence is always 0. It requires 44100 Hz input and is offline/whole-signal (not real-time).
- **Speed:** The TISMIR benchmark reports that for a 5-second segment, most Essentia.js algorithms take 0.46–3.48 s (1.5–6.8% of audio duration), with beat detection, MFCC and pYIN being the slowest; pYIN hit 54.7% of real-time (16.4 s) in the worst case. Beat tracking is among the slowest features. Practically, budget on the order of seconds per track for multifeature beat tracking on a 60–120 s excerpt.
- **Loading / build step:** Distributed as `essentia-wasm.web.js` (async, `<script>`-tag loadable) and `essentia.js-core.js` (IIFE), plus `.umd.js`/`.es.js` sync builds for AudioWorklet/Worker. **No build step; CDN-loadable.** Runs in Node and browsers.
- **Web Worker:** Yes — the UMD/ES WASM backends are documented for AudioWorklet and worker use. Since `AudioContext`/`decodeAudioData` are unavailable in workers, decode on the main thread or via WebCodecs, then pass the Float32 PCM to the worker for analysis.
- **Known limitations:** Rapid API churn (the docs state it is "currently under rapid development … APIs and features will evolve"); some algorithms with unsupported IO wrappers are removed from bindings; WASM memory management can cause the slow-feature outliers noted above; AGPLv3 licensing has implications for closed-source deployment.

**Alternatives:**
- **Meyda** (~20 features, plain JS): good for spectral features/RMS but has no robust beat tracker; less predictable timing than Essentia.js in the benchmark. Use as a lightweight complement, not the tempo engine.
- **aubiojs** (aubio compiled to WASM): exposes `aubio.tempo` (default method) with a known bias toward ~107 BPM and half/double ambiguity; solid onset/tempo but smaller feature set. Viable secondary opinion.
- **music-tempo** (autocorrelation, plain JS): pure-JS, no WASM, easy to drop in; accuracy modest and no beat-phase output.
- **realtime-bpm-analyzer** (dlepaux): TypeScript, Web-Audio-based, real-time from streams/mic; uses a lowpass + peak-interval approach conceptually similar to what you're replacing — good for live BPM but not a fundamental upgrade in ODF quality.
- **web-audio-beat-detector** (chrisguttandin): this is *the Joe Sullivan method*. Do not adopt — it is the same class of algorithm that failed.

**Recommendation:** Essentia.js `RhythmExtractor2013` (multifeature) as primary; aubiojs as an independent cross-check when Essentia confidence is low; Meyda for cheap spectral/energy features.

### 3. Whole-corpus ingestion without per-file selection

- **`showDirectoryPicker()`** (WICG File System Access spec) returns a `FileSystemDirectoryHandle`; recurse with `for await (const entry of handle.values())`, descending into sub-directories for a full corpus scan. This satisfies requirement (a): one gesture, whole library.
- **Permissions/persistence:** Handles are serialisable and can be stored in IndexedDB. Historically permissions did not persist across sessions (crbug.com/1011533); **Chrome 122+ ships persistent permissions** with a three-way prompt when a stored handle's `requestPermission()` is called on next visit. Best practice: store the handle, and on reload call `queryPermission()`/`requestPermission({mode})` behind a user gesture — the first file access after rehydration throws `NotAllowedError` if you skip this (this is the most common real-world failure mode reported for the API).
- **Browser support (2026):** Chromium (Chrome/Edge/Opera) yes. **Firefox and Safari do not implement the disk pickers** — they support only the Origin Private File System (`navigator.storage.getDirectory()`), a sandboxed store the user can't see in their file explorer. On iOS/iPadOS, Safari ships only OPFS. **Provide a `<input type="file" webkitdirectory>` fallback** for non-Chromium browsers; it gives a one-shot read-only `FileList` of a chosen directory tree but cannot persist handles or re-open across sessions.
- **Security restrictions:** Requires a secure context (HTTPS/localhost) and a user gesture; the browser blocks system/sensitive directories and may refuse "too sensitive or dangerous" picks (AbortError).
- **Practical limits:** No hard file-count cap; the constraint is memory (see §4), not enumeration. Directory depth is effectively unlimited for traversal.

### 4. Memory architecture for a large corpus

`decodeAudioData` expands a track to roughly 80 MB of float PCM (a 4-minute stereo track at 44.1 kHz ≈ 42M samples × 4 bytes × 2 ch), so several hundred tracks cannot coexist in memory. The correct architecture:

- **Analyse-then-discard:** decode one track (or a small worker-pool batch), extract features, **release the AudioBuffer immediately**, keep only the compact feature record (BPM, beat grid, key, loudness, energy, downbeat offset — kilobytes per track).
- **Partial decode of an excerpt:** decode only 60–120 s for analysis. The literature supports short excerpts: classic tempo systems operate on 20-second excerpts (ISMIR 2004) or even 3–20 s (US Patent 7,645,929), and comb-filter/autocorrelation trackers use 8-second windows. **For tempo estimation, 30–60 s of steady-beat audio is ample.** For *phrase/structure* detection you need the whole track, but structure can be computed from a decimated energy/MFCC feature stream rather than full-resolution PCM. Note: `decodeAudioData` decodes the whole buffer, so to truly decode only an excerpt use WebCodecs `AudioDecoder` fed a demuxed slice, or decode fully then slice and discard.
- **Persistence:** store feature records in **IndexedDB** keyed by file path + last-modified + size, so re-analysis is skipped on subsequent sessions. This is what makes a several-hundred-track library usable repeatedly.
- **Concurrency:** `AudioContext`/`decodeAudioData` are **main-thread only** (not available in workers). **WebCodecs `AudioDecoder` IS available in dedicated Web Workers** (Chrome/Edge 94+, Firefox 130+, Safari 26+), decodes off the main thread, and supports transferable outputs — but only for AAC/Opus/FLAC/MP3-where-supported, not arbitrary formats. Practical pattern: a pool of **2–4 decode workers** (match to hardware concurrency, diminishing returns beyond physical cores) using WebCodecs, each handing Float32 PCM to an Essentia.js analysis worker. If you must use `decodeAudioData` (broadest format support), decode serially on the main thread but run analysis in workers.

### 5. Genuine beatmatching: beat grid, phase, downbeat

- **Beat grid representation:** two models. A **constant-BPM grid** (single BPM + first-beat offset) is what Mixxx prefers because it snaps to "hard" musical values (80, 96, 120, 144) suited to long-term DJ alignment; the Mixxx manual warns that a **0.02 BPM error causes audible drift over a club-length track**, so constant grids demand accurate BPM. A **per-beat position list** (variable tempo) is more faithful for live/hand-played music. Mixxx's `AnalyzerQueenMaryBeats` produces a variable beat map via the QM Vamp plugin (onset detection + probabilistic beat tracking), then derives a constant BPM from the most common inter-beat region. For synthwave/chiptune (rock-steady programmed tempo), **a constant-BPM grid is appropriate and simplest**; store `{bpm, firstBeatSec, downbeatIndex}`.
- **Downbeat detection:** the portable-in-principle state of the art is **madmom's `DBNDownBeatTrackingProcessor`** (Böck, Krebs & Widmer, "Joint Beat and Downbeat Tracking with RNNs," ISMIR 2016) — an RNN activation + dynamic Bayesian network (HMM) with `beats_per_bar=[3,4]`, default tempo range [55, 215] BPM. **Caveat: madmom is Python/NumPy and has no browser port** — it is not directly usable in a plain-JS no-build app. A recent failure-mode study, "The SMC Blind Spot: A Failure Mode Analysis of State-of-the-Art Beat Tracking" (arXiv:2605.12287), found SOTA trackers produce "confident-but-wrong" activations and, verbatim, that "madmom's DBN defaults to min_bpm = 55, but 45 SMC tracks (21%) have ground truth tempo below that threshold, forcing double-tempo predictions"; lowering min_bpm to 30 raised Beat Transformer's F-measure on those slow tracks from 0.381 to 0.458. The lesson for your engine: **your tempo min/max range must bracket the true tempo or you will get systematic double/half-tempo errors.** In-browser, **the pragmatic downbeat approach is Essentia.js beats + a heuristic**: for strict 4/4 electronic music, pick the downbeat phase (of 4 candidates) that maximises low-frequency/energy salience, exactly as the Vande Veire auto-DJ does with a trained classifier over flux/HFC/CSD features.
- **Mixxx sync model (primary source = Mixxx manual + wiki):** SYNC matches tempo *and* phase. It discards the QM plugin's raw comb-filter BPM in favour of a "constant-region" approach that yields hard musical BPMs. Master Sync designates a sync target (first playing deck with a beatgrid) and aligns other decks' phase to it. Mixxx notes a perfect beatmatch is "nearly impossible" — there is always residual drift, corrected by nudging. Their own wiki documents that **no library reliably does beats-per-measure detection**, so a 4-beats-per-bar assumption is the standard fallback.
- **Scheduling a beat-locked crossfade in Web Audio:** `AudioBufferSourceNode.start(when, offset)` is sample-accurate (Baseline since 2015). To align incoming beat 1 to an outgoing beat boundary: compute the outgoing deck's next downbeat time `T_db` in `AudioContext.currentTime` coordinates, and call `incoming.start(T_db, incomingFirstDownbeatOffsetSec)`. The `offset` seeks into the incoming buffer to its downbeat; `when` fires it exactly on the outgoing downbeat. **Keeping two decks phase-locked over minutes:** because both are constant-rate buffer sources, if their effective BPMs are matched *exactly* they never drift; the risk is BPM-estimate error (Mixxx's 0.02-BPM warning). Options: (a) time-stretch both to an identical target BPM so playbackRate = 1 and periods are integer-locked; (b) periodically re-anchor by scheduling the next phrase's downbeat afresh rather than trusting free-running playback. Do not rely on `playbackRate` for tempo matching if you care about pitch (see §6).

### 6. Pitch-preserving time-stretch in the browser

`AudioBufferSourceNode.playbackRate` changes pitch (chipmunk effect) and is explicitly WontFix in the Web Audio spec for pitch preservation. Options for real-time DJ decks:

- **SoundTouchJS AudioWorklet build (`@soundtouchjs/audio-worklet`)** — WSOLA time-stretch running on the audio render thread (replaces deprecated ScriptProcessorNode). **No build step: ships a pre-bundled `processor.js` and is CDN/npm-loadable.** SoundTouch is comfortably real-time (a budget i7 processes 1 hour of stereo in ~10 s), but has ~100 ms latency and its **main weakness is transient smearing/echo on percussive material** — directly relevant to kick-heavy EDM. Tunable via `sequenceMs`/`seekWindowMs`/`overlapMs`. This is the recommended default: pure JS/WASM, worklet-based, no build.
- **Rubber Band WASM (Daninet/rubberband-wasm)** — higher quality (better transient handling) but higher CPU and >100 ms latency; requires wiring the WASM module yourself. Use if SoundTouch's transient echo is audible on your corpus and CPU budget allows. Quality > SoundTouch; CPU cost also > SoundTouch.
- **Tone.js `GrainPlayer`** — granular pitch/time; simple API but audible graininess; acceptable for effects, marginal for clean beatmatched mixing.
- **Phase-vocoder JS implementations** — good for harmonic material, smear transients (which is why the Vande Veire system splits harmonic/percussive and stretches them separately — phase vocoder for harmonic, WSOLA/OLA for percussive, per Driedger & Müller 2014). This HPSS split is the quality gold standard but is heavier to implement in-browser.
- **`HTMLMediaElement.preservesPitch`** — true by default; the browser does high-quality pitch-preserving stretch natively when you set `audio.playbackRate`. **The catch:** it applies to media elements, and support for it *propagating through `MediaElementAudioSourceNode`* has been inconsistent (Firefox historically did not apply playbackRate/preservesPitch to the source node — Bugzilla 1648277/1517199; Chrome did). **You CAN use a `MediaElementAudioSourceNode` as a deck** — feed an `<audio>` element into the graph and get free, high-quality, native pitch-preserved tempo change. **What is lost:** sample-accurate scheduling (media elements have imprecise `currentTime`/start timing versus `AudioBufferSourceNode.start(when)`), harder loop/cue precision, and cross-browser inconsistency in whether preservesPitch reaches the audio graph. For DJ-grade phase-locked scheduling, the buffer-source + SoundTouch worklet path is more reliable than the media-element path.

**Recommendation:** SoundTouchJS AudioWorklet for the stretch, buffer-source decks for scheduling. Reserve Rubber Band WASM for a "high quality" mode.

### 7. Harmonic mixing

- **Key detection in-browser:** Essentia.js `KeyExtractor` implements the Krumhansl-Schmuckler correlation approach with selectable profiles (Temperley, Krumhansl, **EDMA** — the last derived specifically for EDM). Voting across the three profiles is common practice for robustness.
- **Accuracy on electronic music:** the primary source is Faraldo, Gómez et al., "Key Estimation in Electronic Dance Music" (ISMIR 2016, produced under the EU GiantSteps project, FP7 grant 610591), which introduced the `edma` (auto-extracted), `edmm` (manual) and `edmt` (Temperley) profiles. The EDM-specific profiles outperform generic ones — `edma` gains 25.9 percentage points over default settings on the Beatles set (more modest gains on GiantSteps) — and, critically, they specifically cut the fifth and parallel major/minor errors that generic profiles make. Best weighted MIREX-style scores land in the ~72–76 range on GiantSteps. Commercial in-browser tools using Essentia report ">80% on most popular genres," but treat that as vendor-reported. The dominant error class in EDM key detection is the perfect-fifth neighbour — which, conveniently, is a *harmonically compatible* mix anyway.
- **Camelot wheel:** map each detected key to a Camelot code (1–12 with A=minor, B=major). Compatible moves: same code (perfect), ±1 same letter (perfect fifth/fourth, smooth energy shift), same number opposite letter (relative major/minor, mood change), and +2 or +7 for deliberate "energy boost." Use these as hard constraints or soft penalties in next-track scoring.

### 8. Track selection and set construction

- **DJ practice:** build an **energy curve** — sequence tracks so energy rises toward peaks and eases in valleys, rather than randomly. Combine key compatibility (Camelot adjacency), tempo proximity (small BPM steps or deliberate double/half moves), and energy/loudness trajectory.
- **Research & open source:**
  - **AutoMashUpper** (Davies et al., IEEE/ACM TASLP 2014) — structural segmentation + mashability scoring.
  - **"Automatic Detection of Cue Points for DJ Mixing"** (Zehren, Alunno, Bientinesi; ISMIR 2020 / Computer Music Journal 2022) — detects "switch points" in EDM using novelty analysis + rules distilled from professional-DJ interviews.
  - **Vande Veire & De Bie, "From raw audio to a seamless mix"** (EURASIP JASMP 2018, article 13, DOI 10.1186/s13636-018-0134-8) — the most complete open-source blueprint. Pipeline: custom Davies-style beat tracker (melflux ODF, 1024/512 frames, autocorrelation tempo in a fixed genre range, argmax phase); downbeat via a **logistic-regression classifier trained on 117 annotated songs** using flux/HFC/CSD features + a Viterbi-like max-likelihood trajectory over 4 phases; **phrase/structure via Foote novelty** — two structural similarity matrices (13 MFCCs cosine; RMS energy) with a 64-frame checkerboard kernel, combined by geometric mean, then boundaries snapped to downbeats and constrained to **multiples of 8 measures**. Everything is time-stretched to a fixed target 175 BPM using **HPSS + phase-vocoder (harmonic) + WSOLA (percussive)**. Crossfades are downbeat-aligned with type-dependent lengths (double drop: 16-measure fade-in / 32-measure fade-out; rolling and relaxed: 16/16), with a 3-band EQ "switch point" ensuring only one track's bass+treble sounds at a time. Reported: **~91% of songs fully correctly annotated** (component accuracies ~98.2% beat, ~98.1% downbeat, ~94.3% structure on a 220-song hold-out), validated by an **18-person Drum-and-Bass listener study** rating mixes "high quality." Open-source: `github.com/lenvdv/auto-dj` (Python 2) and `github.com/lenvdv/dnb-autodj-3` (Python 3); a third-party EDM fork (`ddman1101/Auto-DJ`) swaps in madmom for downbeats.
- **Phrase detection is the key to musicality:** landing a transition on an 8/16/32-bar boundary (not an arbitrary beat) is what separates "beatmatched" from "musical." Foote novelty on an MFCC+energy SSM, with boundaries quantised to downbeats and phrase-multiples, is the portable recipe — computable in JS from decimated features without holding full PCM.

## Recommendations

**Stage 1 — Fix detection (highest priority, well-supported by evaluation).**
1. Drop in Essentia.js from CDN (`<script>` tags, no build). Replace the Sullivan detector with `RhythmExtractor2013` in `multifeature` mode; store `{bpm, beats[], confidence}`.
2. Set the tempo search range to bracket your corpus (synthwave ~80–130, chiptune can be faster) and **retain octave alternatives** to combat the half/double error that dominates EDM tempo estimation. Do not set a min so high it forces double-tempo (the SMC Blind Spot lesson).
3. **Confidence gating:** if multifeature confidence is below a threshold you calibrate on the LukHash corpus, cross-check with aubiojs `tempo`; if they agree within tolerance, accept; else flag for manual confirmation. *Benchmark to beat:* median confidence must rise well above the current 0.096, and manual spot-checks should confirm stable grids. If confidence stays low even with multifeature, that empirically confirms chiptune is the hard case, and you fall back to cross-checking + user confirmation.

**Stage 2 — Corpus ingestion and persistence (well-supported on Chromium; common practice).**
4. `showDirectoryPicker()` + recursive `.values()`; store the handle in IndexedDB; re-request permission behind a gesture on reload. Ship a `webkitdirectory` fallback for Firefox/Safari.
5. Analyse-then-discard on a 60–120 s excerpt; persist feature records in IndexedDB keyed by path+mtime+size. Parallelise decode with 2–4 WebCodecs workers where format allows; else main-thread `decodeAudioData` + worker analysis.

**Stage 3 — Real beatmatching (common practice; some parts untested in-browser).**
6. Compute a constant-BPM grid `{bpm, firstBeatOffset, downbeatIndex}`; choose downbeat phase by low-frequency/energy salience (4/4 assumption).
7. Time-stretch both decks to a common target BPM with SoundTouchJS AudioWorklet (no build); schedule with `start(when, offset)` aligning incoming downbeat to outgoing downbeat. Re-anchor each phrase to prevent drift.
8. Do harmonic filtering with `KeyExtractor` → Camelot; score next track by weighted sum of key compatibility, BPM proximity, and energy-curve fit.

**Stage 4 — Musical set construction (research-backed; heavier lift).**
9. Add Foote-novelty phrase detection (MFCC + RMS SSMs, checkerboard kernel, 8-bar-multiple boundary snapping) so transitions land on phrase boundaries. Model the crossfade on the Vande Veire scheme (downbeat-aligned, 16-bar fades, 3-band EQ switch).

**Thresholds that change the plan:** If per-track multifeature analysis exceeds a few seconds on your target hardware, switch to `degara` (faster, but no confidence) or decode shorter excerpts. If SoundTouch transient echo is audible on kicks, escalate to Rubber Band WASM. If you must support Firefox/Safari as first-class, the disk-picker path is unavailable and you should treat `webkitdirectory` (no persistence) as the primary UX there.

## Caveats
- **Chiptune beat tracking is genuinely unstudied** — no published accuracy figures exist for square-wave/noise-percussion audio. Every recommendation for that subset is *untested* and must be validated on your own corpus; expect it to be the hardest case and design the confidence-gated fallback around it.
- **madmom (best-in-class downbeats) has no browser port.** Its algorithms are described here for completeness and as the target quality bar, but in a no-build JS app you must approximate downbeats heuristically or via Essentia + rules.
- **File System Access disk pickers are Chromium-only** as of 2026; Firefox and Safari support only OPFS. Cross-browser reach requires the `webkitdirectory` fallback with no session persistence.
- **Essentia.js is AGPLv3 and under rapid API change** — pin a version, and review licensing for any closed-source/commercial deployment.
- **Vande Veire's reported ~98% beat/downbeat accuracy is on Drum & Bass**, a genre with an exceptionally strong, regular beat; do not assume those figures transfer to synthwave or chiptune. The listener study (n=18) is small.
- **Some GiantSteps ground-truth annotations are disputed:** Schreiber & Müller ("A Crowdsourced Experiment for Tempo Estimation of Electronic Dance Music," ISMIR 2018) found the original GSOrig ground truth "contains incorrect annotations for up to 8.9% of the tracks (ignoring octave errors)," with a further ~0.9% of tracks having essentially no global beat. Treat absolute EDM accuracy numbers as approximate.
- **The 80 MB/track and per-track timing figures are order-of-magnitude estimates** that depend on track length, sample rate, channel count, and device; measure on your target hardware before finalising the worker-pool size.
